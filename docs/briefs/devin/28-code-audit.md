# Devin task 28 — Code and pipeline audit (bug hunt), no UI

You run in your own worktree on a new branch: `git fetch; git checkout -B feat/audit-fixes origin/main`. Commit on your branch is allowed (conventional commits, no AI trailers); push the branch, never main. **Do not edit anything under `web/`** (the UI is owned by another terminal). Your worktree has no `data/` and no `.env`: create a venv (`python -m venv .venv`, install `back/requirements-dev.txt`, and `pip install pytest` plus what `pipeline/` needs if you want to run unit tests on its pure functions); run the back tests (they use `fixtures/`). Never print secrets. The goal is to find real defects before the jury does, in code that will run in production or produce the published data.

## Scope, in this order

1. **Back end (`back/`) as a production service on Vercel Hobby**
   - Input validation on every endpoint: `/api/live` (bbox, window), `/api/risk`, `/api/field/diagnose` (point, ha, polygon: closed ring, vertex cap, self-intersection, antimeridian, poles, NaN and infinity, huge numbers, wrong types, empty body), `/api/field/rotations`, `/api/field/explain`, `/api/geocode` (the query is forwarded to a third party: check for injection into the upstream URL, length limits, empty results, upstream errors, and abuse by repeated calls).
   - Error handling: an exception path must never return a stack trace or an internal path; every upstream failure (FIRMS, POWER, R2, terrain tiles, geocoder, AI provider) must degrade with a clean message and the right status code; look for `except Exception: pass`, unbounded caches (memory growth per instance), caches keyed by user input, race conditions in the in-flight map, timeouts that exceed the Vercel function limit, and CORS configuration (`*` in production is acceptable only for public data: say so explicitly).
   - Security basics: secrets never logged or returned, `DATA_BASE_URL` scheme handling (`file://` must only work in development), SSRF through any URL built from user input, dependency pins with known vulnerabilities (run `pip install pip-audit` and `pip-audit -r back/requirements.txt` if the network allows and report).
   - Correctness of the engine: read `back/app/services/rotations.py`, `measures.py`, `knowledge.py` and the diagnose derivations in `back/app/routers/field.py` and `field_sources.py` for logic errors (off-by-one on day-of-year and leap years, hemisphere assumptions, month wrap-around windows that cross the new year, division by zero, null handling, unit mixups between mm, mm per day and mm per month, percent versus fraction, sign of anomalies, time zones and UTC dates, sorting stability, determinism). Build adversarial synthetic diagnoses and rotations requests and report any crash or absurd output.
2. **Fire pipeline (`pipeline/`) and the model (`model/`)**: read `pipeline/01_ingest.py` to `07_firms_2026.py`, `common.py`, `model_input.py`, `validate_export.py`, `orin_*.py`, `model/fire_risk/*.py`, `model/field_grid/*.py`, `model/analogs/*.py`, `model/power/*.py`. Look for: leakage between train and test, label construction errors, windows that cross year boundaries, week-of-year edge cases (week 53), H3 resolution mixups, UBIGINT versus string conversions, deduplication keys, timezone handling, filters applied twice or not at all, division by zero in factors, silent fallbacks that hide a failure, files written non-atomically, resume logic that skips partial outputs, and any place where a failed download is treated as zero fires. You cannot run the heavy steps (no data here): review the code and write unit tests for the pure functions that you can test with tiny synthetic inputs.
3. **Operational readiness**: `vercel.json`, `api/index.py`, `requirements.txt`, `back/requirements*.txt` (does a clean install run on Python 3.12? are all imports covered? is the function size under the Vercel limit?), `tools/upload_r2.py` (idempotence, partial failure behavior, content types and encoding, the derived credential path), `.gitignore` coverage (nothing sensitive or huge can be committed), and the docs `docs/DEPLOY.md` against what the code really needs (environment variables list complete? any variable the code reads that the guide does not mention?).

## Output

1. `docs/audit/code-audit.md` (English): findings table with id, severity (P0 blocks the demo or leaks something, P1 wrong results or crash on plausible input, P2 robustness, P3 polish), file and line, evidence (a failing test or a reproduction), and status (fixed in this branch, or open with a recommendation). Group by area. List what you checked and found clean, so the team knows the coverage.
2. Fix every P0 and P1 you can, and P2 when the fix is small and safe, each with a regression test in the existing test layout; keep fixes minimal and do not refactor. If a fix would change a documented contract or behavior the other terminals depend on, do not fix it: describe it in the audit.
3. Run all back tests and the validator on `fixtures/` before pushing.
